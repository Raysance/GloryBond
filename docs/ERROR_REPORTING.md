# QQ 错误报告

出现终止性异常时，机器人向本次操作的群发送原生合并聊天记录。卡片展示操作名称、可读原因、时间与报告编号，展开后直接查看原始 Python traceback，包含异常链、完整堆栈、源文件路径、行号、代码行和原始异常消息。管理员继续收到同一编号的私聊诊断。

群命令回到实际触发群，定时推送回到其既定群；私聊操作的内容不会因此转发到公共群。后台重复故障按目标、操作和错误类型每5分钟最多报告一次，新的前台消息独立报告。部分成功的查询保留已有结果，同时报告失败部分，不把整批任务说成全部成功或已回滚。

B站和 X 的 interval 订阅采用连续失败阈值：每个平台、推送群分别统计，检查连续失败30轮或 QQ 投递连续失败30次时才向群和管理员报告一次。一次检查中多个失败只计一轮，部分成功但仍有失败的检查继续累计；成功检查（含无新内容）清零，未执行检查的跳过轮次保持原计数。QQ 投递仅在完整消息获得有效回执后清零，与检查计数独立。持续失败期间不反复通知，恢复后重新开始计数；Redis 保存状态，重启不清零。计数存储故障只记日志，不绕过阈值发送即时报告。主动查询仍即时报告。

覆盖范围包括命令入口、戳一戳、B站/X订阅、每日战报、后台计算及 QQ 消息交付。项目的未捕获 NoneBot matcher 异常和 APScheduler 任务异常也接入同一出口。AI 运行中失败继续沿用已有的详细失败转发及轨迹，准备阶段的异常使用通用错误报告；撤回取消不发送失败通知。

通用错误详情通过 `traceback.format_exception(error)` 生成，不再脱敏、重写或截断。异常对象没有堆栈时，沿用 Python 返回的异常类型与消息；不补造调用记录。网络超时、访问拒绝、限流、资源缺失等按实际异常说明，无法确认的网络故障不直接断言为代理失效。错误文本使用原生文字段，里面的 CQ 文本不会变成 @ 或媒体指令。

QQ 发送超时可能发生在平台已经接受消息之后，因此只报告未确认状态，不自动重发原消息。诊断消息不触发消息自动化，其自身发送失败只记录日志，避免循环刷屏；QQ 或队列完全不可用时，群中也无法收到报告，需要查服务日志。

## 维护入口

- [`errors.py`](../src/glorybond/apps/qq/errors.py)：可读原因、原始 traceback、限频和未捕获异常钩子。
- [`events.py`](../src/glorybond/apps/qq/events.py)：绑定真实事件与群/私聊目标。
- [`scheduler.py`](../src/glorybond/apps/qq/scheduler.py)：后台任务、部分成功和生命周期异常。
- [`interval_jobs.py`](../src/glorybond/apps/qq/interval_jobs.py)：订阅检查与投递的连续失败通知、可信调度来源。
- [`notification_state.py`](../src/glorybond/storage/notification_state.py)：Redis 原子计数与每次连续故障的单次告警标记。
- [`message_sender.py`](../src/glorybond/apps/qq/message_sender.py)：原生合并转发、自动化隔离及发送失败保护。

业务层通过可选 `on_error` 回调把原始异常交给 QQ 适配层，不自行选择群或依赖 NoneBot。恢复成功的内部重试、正常无数据和用户取消不作为终止性异常重复报告。报告组装不调用模型。
